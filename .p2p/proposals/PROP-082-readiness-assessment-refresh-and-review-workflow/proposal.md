# PROP-082 - Readiness Assessment Refresh And Review Workflow

## Status

`draft`

## Problem

The current proposal readiness CLI can bootstrap and refresh readiness snapshots, but it does not provide a governed way to qualitatively reassess an updated proposal, confirm that owner questions have been resolved, raise confidence, update criterion scores, clear failed gates, or import/review an evidence-based assessment. As seen with PROP-006, a proposal can become substantively ready for decision while p2p proposal readiness refresh still keeps the conservative bootstrap score, forcing acceptance to rely on owner override even when the artifacts are actually mature.

## Context

PROP-002 introduced readiness as an advisory maturity model with computed_score, labels, failed gates, owner override, confidence, and criterion evidence. PROP-006 exposed a workflow gap: after the proposal was refined and open questions were resolved, the available commands were only show, init, refresh, and explain. There was no CLI primitive to perform or record a real reassessment through the public P2P interface. Directly editing readiness.yml would violate the managed .p2p boundary, while accepting with override preserves governance but does not solve the assessment workflow.

## Goals

- Add a governed CLI workflow for reassessing proposal readiness after artifacts change.
- Distinguish bootstrap, refresh, assess, review, gate resolution, import, and owner override semantics.
- Allow criterion-level scores, confidence, failed gates, missing items, suggested next actions, and evidence to be updated through public P2P commands.
- Preserve the distinction between computed analytical readiness and owner override.
- Expose equivalent MCP tools once CLI behavior is stable enough to share through the same core implementation.

## Non-Goals

- Automatically deciding proposal acceptance on behalf of the owner.
- Falsifying computed_score when the owner uses override.
- Replacing proposal artifacts with readiness metadata as the source of truth.
- Building a perfect AI evaluator in the first iteration.

## Proposal

Introduce a readiness review workflow under p2p proposal readiness. Keep init as conservative bootstrap. Keep refresh as snapshot synchronization. Add an assess/review path that reads proposal artifacts, records criterion-level evidence, updates scores, confidence, failed gates, missing items, and suggested next actions, and marks whether the assessment is deterministic, agent-assisted, or owner-reviewed. Add a gate-resolution path for cases where an owner explicitly confirms that a gate such as owner_questions_resolution has been resolved. Add an import path for structured assessment files generated by agents or external review processes, with validation before persistence. All write operations must preserve profile_id, profile_version, computed_at, assessment source, reviewer/actor, and audit notes. Owner override remains a decision-time governance event that can set effective readiness without overwriting the computed score.

## Acceptance Criteria

- p2p proposal readiness init remains a conservative bootstrap command.
- p2p proposal readiness refresh does not pretend to perform qualitative reassessment unless it actually re-evaluates criteria.
- A new assess or review command can update criterion-level scores, confidence, failed gates, missing items, suggested next actions, and evidence through the CLI.
- The workflow can clear owner_questions_resolution when the owner or reviewer records an explicit resolved decision with a reason.
- Readiness assessment changes are persisted without manual edits to readiness.yml.
- Assessment records distinguish deterministic, agent-assisted, and owner-reviewed sources.
- Owner override remains separate from computed_score and is preserved as an effective governance status or decision event.
- p2p validate detects malformed readiness assessment records.
- MCP read/write tools can expose the same behavior through shared core logic without bypassing CLI safety semantics.
