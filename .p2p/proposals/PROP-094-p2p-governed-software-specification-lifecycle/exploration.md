# Exploration - P2P-Governed Software Specification Lifecycle

The refined problem is a workflow problem, not only a persistence problem. The file of specs is useful, but it should come after P2P has captured enough project definition and decisions to make the spec traceable.

The software vertical should expose the ingredients that a future spec needs. The agent should use that vertical to guide the owner through missing pieces instead of writing a standalone file immediately.

The expected flow is:

1. identify the owner request type;
2. fill missing software-vertical fields;
3. create or update one or more proposals for meaningful decisions;
4. use choices where alternatives conflict;
5. accept enough direction to support implementation work;
6. create a Change Set;
7. generate a P2P-native software spec;
8. export a specs file only as a downstream artifact.

Exploratory spec outlines remain allowed, but they should be chat or P2P exploration material unless explicitly exported.
