# Clarifications - P2P-Governed Software Specification Lifecycle

The owner agreed to refine PROP-094 around the following direction:

- The need for specs belongs inside the software vertical.
- A specs file should be a downstream artifact, not the starting point or primary source of truth.
- The contents needed for a useful spec may be defined through one or more P2P proposals.
- Complex software specs should be assembled from accepted or explicitly provisional P2P state: proposals, choices, readiness, decisions, and Change Sets.
- Readiness is advisory for exploratory spec discussion, but implementation-oriented specs and downstream exports should require an accepted direction and relevant Change Set.
- Preliminary specs should remain in chat or P2P exploration/proposal material until the owner asks for a durable export or stable document.
- Generated instructions and docs should include a concrete routing table for "user asks for specs" requests.

This resolves the earlier open questions in favor of software-domain guidance, P2P-governed spec ingredients, and downstream file export.
